# 编年史结构模板与写作风格

本文定义《项目开发编年史》的标准结构。写作时严格按此模板组织,可保证多篇编年史风格一致、可溯源、可对照。结构参考 Zircon 项目的开发编年史笔记(从 0 到 1 的七年)。

## 先看这个,单章硬要求清单

写每一章之前对一遍,九条全中才算合格。

- [ ] h2 章节标题带类型、事件与提交数,如 `## §2 2026 初创 · 从写作技能到出版工具(35 条)`
- [ ] 一句话开头,带画面或动作,不是"本章概述"
- [ ] 数据速览引用块,含提交数、活跃作者数、tag 数与版本范围
- [ ] 正文两到三段连贯叙述,覆盖阶段定位、核心问题、解决方案,不贴标签
- [ ] `### 事件批次` 分节标题(三级标题,不是粗体)
- [ ] 至少两个 `#### 批次 NN,主题` 四级标题
- [ ] 提交行用无序列表,每条带真哈希与一句话说明
- [ ] `### 本章之变` 一段,写清换来了什么、代价、遗留
- [ ] `### 本章关键词` 三到五个,用反引号包裹

## 整体结构

| 部分 | 内容 |
|---|---|
| 题头元信息 | 日期、数据来源(如"488 条 git 提交逐一核对")、关联笔记、核心结论(全文浓缩版) |
| 三幕梗概 | 起因 → 转折 → 现状,约 300–800 字,关键论断带代表 commit / release |
| §0 项目是什么 | 项目背景、全景数字表、年度提交量 ASCII 条形图 |
| §1 人物图鉴 | 作者表格,含提交数、活跃期、贡献路径与代表提交;每章在此对应一行贡献者指纹 |
| §2 到 §9 编年史主体 | 按年分章(章数随项目年龄增减) |
| §10 尾声 | 三到五条经验总结 |
| §11 论坛回声 | 与 git 主线并行的社区史 |
| 附录 A | 全部 PR 编号时间线(含年份与主题标注,★ 标记重大事件) |
| 附录 B | 本地 fork 的提交完整清单(存在 fork 场景时) |
| 附录 C | 论坛抓取数据,含帖子年度分布、热门帖 TOP N、关键帖 URL 速查 |
| 附录 D(可选) | 代码存活、年代队列与技术债证据,链接回对应章节 |
| 文末注 | 数据方法论,写清 git log 含 merge、PR 编号提取规则、提交者日期与时区口径 |

## 题头元信息

文档开头写 frontmatter 存结构化元数据,转换脚本直接读取,正文里不必重复。

```markdown
---
title: 项目开发编年史,从 0 到 1 的七年
author: 整理者名
date: 2026-08-07
lang: zh
---

# 《项目开发编年史,从 0 到 1 的七年》

> 整理日期 2026-08-07
> 数据来源 N 条 git 提交逐一核对、M 个 release、K 个 issue、论坛 P 帖、新闻 Q 篇
> 核心结论 一句话浓缩全文(如"一个人撑起 80%,社区接力补完")
```

结论先行。题头即给出全文浓缩版结论,后续所有章节都是该结论的展开论证。frontmatter 的 title 与正文 h1 保持一致,date 与引用块里的整理日期一致。

## 三幕梗概

题头后、§0 前固定放 `## 三幕梗概`,用 `### 起因`、`### 转折`、`### 现状` 三段串起全书,正文合计约 300–800 字(不计链接目标)。起因交代项目最初要解决的具体问题,转折选改变方向或使用方式的事件,现状写到本次截点为止解决了什么、还留下什么。关键论断就近挂代表 commit、固定版本文件或 release 链接;每幕至少一处证据。证据不足就缩短,不为了三幕补写危机、动机或社区态度。

梗概作为独立阅读入口,正文仍保留完整编年。README 或在线书首页可以引用同一段梗概并链接全文,不要另写一个时间范围不同的宣传摘要。已发布编年史增量续写时保持原梗概,在新增章节写明新截点;如何追加见 [增量续写](incremental.md)。可核查实例见 [本仓库编年史](../examples/repository-chronicle.md#三幕梗概)。

## 章节类型词表

默认标题采用 `## §N <年份或里程碑> <类型> · <具体事件>(<提交数> 条)`。中文正文用中文类型,英文正文用英文类型,无需在每个标题重复双语。

| 中文类型 | 英文类型 | 选用依据 |
|---|---|---|
| 初创 | Founding | 首次可运行原型、首个公开版本或仓库建立 |
| 成长 | Growth | 功能、使用范围或维护能力持续扩展,有代表提交支撑 |
| 平静 | Quiet | 已覆盖时间窗口内提交活动较低;不能由此推断项目死亡或作者离开 |
| 危机 | Crisis | 有可核实的事故、关键回退或中断记录;低提交量本身不够 |
| 重写 | Rewrite | 大范围替换实现或迁移架构,比较变更前后的树与关键文件 |
| 社区涌入 | Community Surge | 新贡献者或社区参与增加,既有统计也有来源,不能只凭 star 数命名 |

每章选最能解释主线的一类,事件名必须具体。一个年份可以包含多个阶段,必要时分里程碑章并注明不重叠的提交范围;不要强迫每个类型在一本书里都出现。允许项目自定义词表,在方法论列出名称、含义、选用依据,全书保持一致。已有章节的历史标题在增量续写时保留。

### 贡献者指纹与贡献地图

在人物图鉴中按章列出主要贡献者、新出现的作者、修改路径与代表提交;也可以放在附录,正文相关段落链接过去。这样保留单章固定结构,同时能看见人的接力。

| 章节 / 范围 | 主要贡献者 | 首次出现 / 持续参与 | 路径与本章主线 | 代表 commit |
|---|---|---|---|---|
| 年份或两个截点 | 作者的公开署名 | 全仓库首次出现时间;本章是否新作者 | 文件或目录、可验证的改动 | 至少一条可点击提交 |

用与正文一致的范围核对,以下命令中的 `BASE..HEAD` 换成已解析的提交范围,首次全量分析用截点 SHA。路径限定时 Git 会简化历史,只把它用作贡献线索,不能拿路径提交数加总成全仓总数。

```bash
git shortlog -sne BASE..HEAD
git log BASE..HEAD --format='%H %cI %aN <%aE>' --name-only -- src/
git log --reverse --format='%H %cI %aN <%aE>' HEAD
```

记录是否采用 `.mailmap`、是否包含 merge、是否计入机器人和共同作者 trailer,与统计表口径保持一致。没有身份合并依据时保留不同署名并说明;发布版本遵守用户匿名化偏好,不需要展示邮箱。“新进入核心圈”须有持续贡献或维护者记录支持,否则写“本章首次出现”。新作者不存在时明确写“无”,不要为了人物故事虚构接班人。

## 组件运用总则

标题与列表组件按固定层级使用,让结构一眼可读。

| 组件 | 用在哪 | 示例 |
|---|---|---|
| h1 | 书名(全文唯一) | `# 《项目开发编年史,从 0 到 1 的七年》` |
| h2 | 章节与附录 | `## §2 2026 初创 · 从写作技能到出版工具(35 条)` |
| h3 | 章节内结构分节 | `### 事件批次`、`### 本章之变` |
| h4 | 批次编号 | `#### 批次 01,消息通道的可靠性` |
| 引用块 | 题头元信息、数据速览、核心结论 | `> 本月 288 条提交,2 位活跃作者` |
| 有序列表 | 流程步骤、检索顺序 | 1. 克隆 2. 粗查 3. 归纳 |
| 无序列表 | 提交行罗列、附录清单、关键词 | `- `哈希` **#PR 标题**(作者) 说明` |
| 表格 | 全景数字、人物图鉴、热度对照 | 见 §0、§1 模板 |
| frontmatter | 题头元数据(标题、作者、日期、语言) | 见题头模板,转换脚本可读 |
| 脚注 | 来源细粒度标注 | `文字[^1]` 文末 `[^1]: 来源 URL` |
| 警示框 | 推断、注意事项,与正文区分 | `::: warning 推断` 内容 `:::` |
| 高亮标记 | 关键数字、核心结论 | `==16,537 条==` 单章不超过三处 |
| 折叠 | 长清单收纳(抽样明细、完整提交表) | `<details><summary>标题</summary>内容</details>` |

不要越级跳层(章节直接塞提交行),也不要为凑层级硬套组件。提交行用无序列表后,批次内不再出现"一段一条提交"的段落堆叠。

脚注与警示框的写作规则如下。

- **脚注**。正文引用新闻、issue、论坛帖时,在句末挂脚注 `[^1]`,文末统一写 `[^1]: 来源标题与 URL`。脚注内容必须真实可点开,不给没有来源的论断造脚注。来源只在脚注里出现一次,正文不重复写 URL。
- **警示框**。推断与注意事项用 `::: warning 推断` 包裹,框内保留「[推断:…未证实]」标注与依据。普通事实段落不要套框,警示框每章最多一处。
- **高亮**。数据速览里的关键数字、阶段判断里的核心结论用 `====` 高亮,单章不超过三处,防止高亮失效。

[本仓库编年史](../examples/repository-chronicle.md) 使用固定截点 `52aa9478714e3b3ce5b5b05bc3b56d160ec9efa1` 的真实 Git 记录,展示三幕梗概、类型标题、活动图、贡献者指纹和时光机锚点。统计范围、复现命令与未获取数据都在样章文末。写作时复用结构,不要复用其中的数字、人物、哈希或结论。

## 按年章节骨架(§2 到 §9)

每章固定段落结构。单章信息量必须能独立回答"这章发生了什么、为什么、之后怎样"三个问题,更要有产品演进视角,每个阶段都要说清定位、主要问题、解决方案。数据速览与本章之变是硬要求,事件批次至少要有一个展开到"来龙去脉"的提交。

成文形式,正文写连贯段落,不要用"阶段定位。""核心问题。""解决方案。"这类标签句把每段钉死。定位、问题、方案是写作时的检查清单,确认素材都写到了,但读起来是一篇连贯的叙述,不是带标题的条目。每个要素一两句话到一段,按叙事流自然衔接。

### 1. 一句话开头

概括本章主题,例如 "AndyF 全面回归,44 条提交把客户端 UI 和玩法系统翻了个遍。"

### 2. 数据速览(硬要求)

一行数字,读者对本章规模先有体感。

```markdown
> 本月 2,087 条提交,11 位活跃作者,5 个版本(v1.0.4 到 v1.3.0),作者数从 2 跳到 11
```

数据从 per_year.tsv、per_month.tsv、per_author.tsv、tags.tsv 来,数字必须与统计一致。活跃作者数、版本数、代表版本号三项必备,有 PR 数据的加 PR 数。数据速览用引用块,是全文唯一允许"标签加内容"的格式。为什么,它承担"一眼看到规模"的功能,标签化在这里是功能;正文的定位、问题、方案反而要融入段落,避免条目感。

月度作者数本身就是一条叙事线。连续几个月列出来,社区规模曲线(2 人到 654 人再到 151 人)可以成为贯穿全书的线索,爆发、峰值、退潮都在数字里,§1 人物图鉴末尾也可以放这条曲线。

### 3. 阶段定位与背景(硬要求,融入段落)

一到两段,回答三个问题,这个阶段项目在做什么,处于什么位置(原型期、产品期、平台期、基建期),外部环境如何(新闻、市场、社区事件、人事变动)。定位要具体到本阶段,不能是放之四海皆准的空话。背景动机(上一章的伏笔在这章兑现、技术趋势)与定位写在一起,不要另起标签段。

### 4. 核心问题(硬要求,融入段落)

本阶段的主要矛盾,写具体、可溯源。问题必须来自材料,提交在修的 bug、issue 里的呼声、新闻里的事件、数据里的拐点(作者数暴跌、提交量腰斩)。写清楚"不解决会怎样",给问题以分量。可以单独成段,但段落本身是连贯叙述,不是给段落贴"核心问题"标签再加一句话。

### 5. 解决方案(硬要求,融入段落)

本阶段怎么解决,一段连贯叙述,与事件批次呼应。有取舍的写明取舍(为什么选这个、放弃了什么,例如"语义化版本在日更节奏下撑不住了,日期版本制是发布机器提速的必然结果")。没有一次解决的,写明"只解决了什么、什么留给后面"。

### 6. 事件批次(用三级标题)

用 `### 事件批次` 作为小节标题,它是章节内的结构分节,不是普通段落。为什么,结构分节用标题而非段落,阅读器与 VitePress 大纲能直接跳转。

批次标题用四级标题,写成 `#### 批次 01,消息通道的可靠性`。为什么,批次是最细的叙事单元,h4 让大纲能折叠到批次级,并与 h3 分节、h2 章节形成完整层级。批次标题带序号,同主题的提交组成一批。例如 2023 年拆为"01/02 技术栈现代化、02/04 装备兼容、05/07 聊天对话框、09/10 技能公会、11/12 收尾"五个批次。批次内按时间先后罗列提交。

批次内的提交行用无序列表,每条提交一行,`-` 开头。为什么,一行式提交行用列表比段落更紧凑,批次的信息密度一眼可见。展开写的重大提交同样用列表项,说明接在标题后面,不另起段落。批次标题后直接跟提交行、没有引导句的,提交行同样转列表。叙述中顺带提到的提交引用(如"11 月 25 日当天 `chore: release 1.2.1` 连着出现")保持叙述,不强行拆列表。

```markdown
#### 批次 01,消息通道的可靠性

第一批提交里,WhatsApp 会话自愈和看门狗占据了显眼位置。

- `Add auto-recovery from stuck WhatsApp sessions`、`Increase watchdog timeout to 30 minutes` WhatsApp 会话卡死自动恢复,看门狗超时调到 30 分钟。一个把身家押在消息通道上的助手,第一件事就是保证通道不死。
- `feat: same-phone mode with echo detection and configurable marker` 同手机模式与回声检测,解决 AI 自己回复自己的回声循环。
```

每个批次至少挑一条重大提交展开写来龙去脉(背景、改动、后果),不能只有一行式罗列。批次之间有承接关系的,写明因果。失败与回退的提交(改错了再改回来)如实写,不回避;关键人物的进场离场、社区呼声到代码落地,都在批次里体现。

**动机链(为什么比改了什么更重要)**。展开重大提交时,能拿到"为什么"的材料就写动机,PR body 里的问题说明、关联 issue 的标题与讨论、提交消息原文。数据来源是 prs.json 的 body 字段与 pr_issue_links.tsv(Closes #X 关联)。写法示例如下。

**引用链接规则**。正文叙事中提到的 PR 与 issue 编号一律加跳转链接,格式 `[PR #87273](https://github.com/<owner>/<repo>/pull/87273)` 与 `[issue #43](https://github.com/<owner>/<repo>/issues/43)`,链接指向编号所属的仓库(本仓库,或 fork 场景下的源仓库)。提交消息原文、代码块、Mermaid 图内的编号是机器字段,不加链接。范围描述("PR 从 #3677 打到 #5807")不逐个链接,保持文本。附录 A 的 PR 编号同样带链接。

```markdown
用户在 Talk 直连 OpenAI Realtime 时收到原始启动认证错误,错误里还带凭据相关的 provider 文本。PR #87273 的说明写的就是这个问题,BSG2000 的修复目标是让这类错误不再把敏感文本暴露给用户。
```

- 有 issue 关联的写明链条,issue #X 提出(时间,讨论热度)→ PR #Y 解决 → 提交落地 → release。
- 只有 PR body 没有 issue 的,用 PR 自己的动机说明。
- 都没有的,不强行编链,一行式提交行即可。动机链只对能串起来的事件写,不注水。

### 7. 提交行模板(每条固定一行)

```markdown
`哈希前7位` **[#PR号](https://github.com/<owner>/<repo>/pull/PR号) 标题**(作者)+ 一句话说明该提交做了什么、为什么
```

举一个例子。
```markdown
`f4fc91f` **#31 .Net Core Server** 服务端从 .NET Framework 迁到 .NET Core,重大架构事件,服务端从此跨平台。
```

- 无 PR 编号的提交省略 `**#N 标题**`,只保留标题。
- 一句话说明必须回答"做了什么"和"为什么",重大事件要显式点出影响(如"从此跨平台""为 2026 年的 Linux 部署埋下伏笔")。
- 戏剧化叙事可用(伏笔、红利、反叛),但必须以事实为骨,不编造因果。

### 时光机锚点

架构转折、对外行为变更与重大删除的结论旁,除 commit 哈希外至少给一个当时树或文件的固定链接,或可复制的只读命令。普通修字提交仍可只列哈希。链接必须使用完整提交 SHA,不能使用会移动的 `main`、`HEAD` 或 tag 别名。

| 要核对的内容 | 锚点格式 |
|---|---|
| 当时的目录与模块边界 | `[当时的树](https://github.com/<owner>/<repo>/tree/<完整SHA>)` |
| 当时的实现或说明 | `[当时的文件](https://github.com/<owner>/<repo>/blob/<完整SHA>/<path>#L<行号>)` |
| 具体变更 | `git show <完整SHA> -- <path>` |
| 读取旧文件 | `git show <完整SHA>:<path>` |

行号必须从该 SHA 的文件核对,路径含特殊字符时对 URL 路径分段编码。重大删除要同时指向删除提交与删除前的文件,用 `git rev-parse <删除SHA>^` 解析父提交后再填链接;根提交没有父提交,不要造一个。迁移则给变更前后两个锚点,说明比较范围。默认使用 `git show`,无需 checkout 或覆盖读者当前工作区。样章包含 [EPUB、在线书和校验规则的三处锚点](../examples/repository-chronicle.md)。

### 8. 本章之变(硬要求,用三级标题)

用 `### 本章之变` 作为小节标题(原因同事件批次,分节可跳转)。一段讲"这章结束时项目变成了什么"。承接上一章结尾,回答读者最自然的追问(这章的努力换来了什么,代价是什么,什么遗留问题留给下一章)。只写本章真实发生的变化,不提前透支后面章节的内容。

### 9. 本章关键词(用三级标题)

用 `### 本章关键词` 作为小节标题。结尾提炼三到五个主题词,例如 `架构迁移` `跨平台` `社区回归` `工具链`。

## §10 尾声(经验总结)

三到五条,常见母题按项目实际调整。

- 个人撑起项目 / 团队分工
- 架构复利。早期架构决策如何影响多年后的演进
- 社区价值。issue、论坛呼声如何决定方向
- 技术栈跟随时代。老框架到新框架的迁移动机
- 项目定位。它是什么、不是什么

## §11 论坛回声

与 git 主线并行,分小节叙述,常见的小节有这些。

- 发布之夜。首个 release 帖的社区反应
- 两位开发者 / 核心人物。社区眼中的作者
- 跨平台种子。社区对平台支持的呼声史
- 玩家/用户社区。多年痕迹(如中国玩家的语言需求演变)
- 全球化。多语言 issue、多国参与者
- 热度对照。论坛新帖数对 git 提交数,逐年对照表
- 互文时刻。三个"先有呼声、后有落地"或"代码先行、社区跟进"的时刻,逐条列出论坛帖与对应提交

热度对照表格式。

| 年份 | 论坛新帖数 | git 提交数 | 备注 |
|---|---|---|---|
| 2019 | 12 | 23 | 发布之夜 |
| 2021 | 2 | 9 | 双沉寂 |

## 附录规范

### 附录 A PR 时间线

按年份列出全部 PR,`[#N](https://github.com/<owner>/<repo>/pull/N) 标题(年份,★ 主题标注)`。★ 用于重大事件,文末注明图例。

### 附录 B 本地 fork 提交清单

存在上游 + 本地 fork 场景时,单独列出 fork 的每条提交(哈希、标题、日期、说明),与上游主线区分。

### 附录 C 论坛数据

- 帖子年度分布表
- 热门帖 TOP N(标题、作者、日期、回复数、浏览数)
- 关键帖 URL 速查表(编号、标题、链接)

### 附录 D 可选附录：代码存活

多年老仓库、大规模 rewrite 或明确的“旧实现还剩多少”问题适合生成此附录。短历史、文档型仓库或数据不足时可以跳过,在方法论说明原因。正文继续讲改动的动机、取舍与结果,附录只补充数量证据。

可复用 [git-of-theseus 官方工具](https://github.com/erikbern/git-of-theseus),按其当前 README 与 `--help` 安装和选参数。已有工具环境时,在独立输出目录运行下列命令;保留原始 JSON 与工具版本,不要只保存截图。

```bash
git-of-theseus-analyze /path/to/repo --outdir /path/to/analysis
git-of-theseus-stack-plot /path/to/analysis/cohorts.json
git-of-theseus-survival-plot /path/to/analysis/survival.json
```

年代队列图展示各年份引入代码在后续快照的存量。工具的总体存活曲线是跨提交聚合的年龄估计,不能直接当作某次 rewrite 的前后存活率。若要报告该事件的存活率,另用可追踪行来源的分析结果,明确分母为改动前范围内的代码行、分子为其在改动后仍可识别的行,同时列出两个完整 SHA。没有可靠的行来源映射时只展示队列图,不硬算百分比。

导入外部结果时记录仓库与分支、起止 SHA、采样日期与时区、路径/后缀范围、排除的生成代码与依赖、空行和注释口径、重命名/移动处理、工具版本、完整命令及原始数据路径。修改格式或移动文件可能改变行归属;存活久不等于技术债,删除多也不等于质量提升。技术债判断仍须关联 issue、测试、维护记录等独立证据。

正文在对应“本章之变”末尾写 `[代码存活口径与图](#附录-d-代码存活)`,附录用 `[返回重写章节](#对应章节锚点)` 链回事件,实际锚点以导出平台渲染结果为准。图注写清比较范围和限制,不得用附录代替主线故事。

## 数据方法论注记(文末)

文末注记要固定写清这几项。

- git log 含 merge 与否
- PR 编号提取规则(从提交消息提取 `#N`,排除误匹配)
- 年份口径(默认按 `%cI` 提交者时间的原偏移年月聚合;它不等于默认分支合入时间,若使用 PR `mergedAt` 或统一时区须另行注明)
- 大仓库抽样口径(如"仅精读里程碑窗口内提交")
- 论坛覆盖率(如"34 页、667 帖元数据,解析出 633 条;关键帖经镜像交叉验证")
- 推断清单(所有 `[推断:…未证实]` 项的汇总)

## 写作风格硬性要求

分两层。第一层五条是底线,与 SKILL.md 的七条铁律同源,是它的浓缩版,任何情况都要守住。第二层八条是"活人感"要求,让文字读起来像人写的,能力允许就都做到。

### 第一层,五条底线

1. **数字可核对**。正文出现的每个统计数字都能在脚本输出里找到,两处不一致就以脚本为准。
2. **提交可溯源**。每条提交行带真哈希(取 commits.tsv 前 7 位),PR 与 issue 编号带链接。
3. **推断有标注**。未证实的判断句末加 `[推断:依据,未证实]`,文末方法论汇总所有推断。
4. **结构不走样**。章节内三个分节标题固定为 `### 事件批次`、`### 本章之变`、`### 本章关键词`,批次用 `#### `。
5. **不编造**。拿不到的数据写"未获取",不用"大约""可能有""据推测"填空。

### 第二层,八条活人感要求

参考 human-writing 的默认散文写法,逐条对照。

6. **开头碰到事情**。章节的一句话开头要有画面或动作,不要"本章概述"式的起手。宁可从一个反常的小事实讲起("开源当天连发四个版本"),不要预告结构。
7. **句长有节奏**。长句讲事实,短句压判断。不要所有句子等长,也不要用"更深一层""真正的问题"之类路标推进。后段接住前段留下的问题,靠材料和因果衔接,不靠连接词。
8. **动作与场景**。展开重大提交时写具体动作,谁、何时、什么状态、原话。动作、细节、原话已经把情绪写出来,就停,不要追在后面解释。
9. **原话先行**。提交消息原文、文档原话、人物引语,有材料就引用,比转述有力。判断可以偏,可以有情绪,把依据放旁边。
10. **具体胜过抽象**。数字、哈希、版本号保留;抽象总结句必须有具体支撑,一句话能换进十篇别的文章,说明它没有当前材料。
11. **失败与自我修正**。改错了再改回来、起初以为后来发现,如实写,这是真实感的来源,不要只写成功。
12. **不表演**。戏剧化来自事实本身,不堆大词,不穿论坛服装。判断直接下,不先立误解再推翻。
13. **双线并行不混写**。git 主线(§2 到 §9)与论坛社区史(§11)分列,靠"互文时刻"交叉引用。fork 或重写的仓库,把上游历史与本仓库的故事勾连。
