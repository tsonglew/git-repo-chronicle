# 编年史结构模板与写作风格

本文定义《项目开发编年史》的标准结构。写作时严格按此模板组织,可保证多篇编年史风格一致、可溯源、可对照。结构参考 Zircon 项目的开发编年史笔记(从 0 到 1 的七年)。

## 整体结构(11 个正文部分 + 3 个附录)

| 部分 | 内容 |
|---|---|
| 题头元信息 | 日期、数据来源(如"488 条 git 提交逐一核对")、关联笔记、核心结论(全文浓缩版) |
| §0 项目是什么 | 项目背景、全景数字表、年度提交量 ASCII 条形图 |
| §1 人物图鉴 | 作者表格,含提交数、活跃期、角色定位 |
| §2 到 §9 编年史主体 | 按年分章(章数随项目年龄增减) |
| §10 尾声 | 三到五条经验总结 |
| §11 论坛回声 | 与 git 主线并行的社区史 |
| 附录 C | 论坛抓取数据,含帖子年度分布、热门帖 TOP N、关键帖 URL 速查 |
| 附录 A | 全部 PR 编号时间线(含年份与主题标注,★ 标记重大事件) |
| 附录 B | 本地 fork 的提交完整清单(存在 fork 场景时) |
| 文末注 | 数据方法论,写清 git log 含 merge、PR 编号提取规则、年份以合入日期为准 |

## 题头元信息

```
# 《项目开发编年史,从 0 到 1 的七年》

> 整理日期 2026-08-07
> 数据来源 N 条 git 提交逐一核对、M 个 release、K 个 issue、论坛 P 帖、新闻 Q 篇
> 核心结论 一句话浓缩全文(如"一个人撑起 80%,社区接力补完")
```

结论先行。题头即给出全文浓缩版结论,后续所有章节都是该结论的展开论证。

## 按年章节骨架(§2 到 §9)

每章固定段落结构。单章信息量必须能独立回答"这章发生了什么、为什么、之后怎样"三个问题,更要有产品演进视角:每个阶段都要说清定位、主要问题、解决方案。数据速览与本章之变是硬要求,事件批次至少要有一个展开到"来龙去脉"的提交。

成文形式:正文写连贯段落,不要用"阶段定位。""核心问题。""解决方案。"这类标签句把每段钉死。定位、问题、方案是写作时的检查清单,确认素材都写到了,但读起来是一篇连贯的叙述,不是带标题的条目。每个要素一两句话到一段,按叙事流自然衔接。

### 1. 一句话开头

概括本章主题,例如 "AndyF 全面回归,44 条提交把客户端 UI 和玩法系统翻了个遍。"

### 2. 数据速览(硬要求)

一行数字,读者对本章规模先有体感。

```markdown
> 本月 2,087 条提交,11 位活跃作者,5 个版本(v1.0.4 到 v1.3.0),作者数从 2 跳到 11
```

数据从 per_year.tsv、per_month.tsv、per_author.tsv、tags.tsv 来,数字必须与统计一致。活跃作者数、版本数、代表版本号三项必备,有 PR 数据的加 PR 数。数据速览用引用块,是全文唯一允许"标签加内容"的格式。

月度作者数本身就是一条叙事线。连续几个月列出来,社区规模曲线(2 人到 654 人再到 151 人)可以成为贯穿全书的线索,爆发、峰值、退潮都在数字里,§1 人物图鉴末尾也可以放这条曲线。

### 3. 阶段定位与背景(硬要求,融入段落)

一到两段,回答三个问题:这个阶段项目在做什么,处于什么位置(原型期、产品期、平台期、基建期),外部环境如何(新闻、市场、社区事件、人事变动)。定位要具体到本阶段,不能是放之四海皆准的空话。背景动机(上一章的伏笔在这章兑现、技术趋势)与定位写在一起,不要另起标签段。

### 4. 核心问题(硬要求,融入段落)

本阶段的主要矛盾,写具体、可溯源。问题必须来自材料:提交在修的 bug、issue 里的呼声、新闻里的事件、数据里的拐点(作者数暴跌、提交量腰斩)。写清楚"不解决会怎样",给问题以分量。可以单独成段,但段落本身是连贯叙述,不是"核心问题:"加一句话。

### 5. 解决方案(硬要求,融入段落)

本阶段怎么解决,一段连贯叙述,与事件批次呼应。有取舍的写明取舍(为什么选这个、放弃了什么,例如"语义化版本在日更节奏下撑不住了,日期版本制是发布机器提速的必然结果")。没有一次解决的,写明"只解决了什么、什么留给后面"。

### 6. 事件批次(用三级标题)

用 `### 事件批次` 作为小节标题,它是章节内的结构分节,不是普通段落。同主题的提交组成一批,批次标题带序号。例如 2023 年拆为"01/02 技术栈现代化、02/04 装备兼容、05/07 聊天对话框、09/10 技能公会、11/12 收尾"五个批次。批次内按时间先后罗列提交。

每个批次至少挑一条重大提交展开写来龙去脉(背景、改动、后果),不能只有一行式罗列。批次之间有承接关系的,写明因果。失败与回退的提交(改错了再改回来)如实写,不回避;关键人物的进场离场、社区呼声到代码落地,都在批次里体现。

**动机链(为什么比改了什么更重要)**。展开重大提交时,能拿到"为什么"的材料就写动机:PR body 里的问题说明、关联 issue 的标题与讨论、提交消息原文。数据来源是 prs.json 的 body 字段与 pr_issue_links.tsv(Closes #X 关联)。写法示例:

```markdown
用户在 Talk 直连 OpenAI Realtime 时收到原始启动认证错误,错误里还带凭据相关的 provider 文本。PR #87273 的说明写的就是这个问题,BSG2000 的修复目标是让这类错误不再把敏感文本暴露给用户。
```

- 有 issue 关联的写明链条:issue #X 提出(时间,讨论热度)→ PR #Y 解决 → 提交落地 → release。
- 只有 PR body 没有 issue 的,用 PR 自己的动机说明。
- 都没有的,不强行编链,一行式提交行即可。动机链只对能串起来的事件写,不注水。

### 7. 提交行模板(每条固定一行)

```markdown
`哈希前7位` **#PR号 标题**(作者)+ 一句话说明该提交做了什么、为什么
```

举一个例子。
```markdown
`f4fc91f` **#31 .Net Core Server** 服务端从 .NET Framework 迁到 .NET Core,重大架构事件,服务端从此跨平台。
```

- 无 PR 编号的提交省略 `**#N 标题**`,只保留标题。
- 一句话说明必须回答"做了什么"和"为什么",重大事件要显式点出影响(如"从此跨平台""为 2026 年的 Linux 部署埋下伏笔")。
- 戏剧化叙事可用(伏笔、红利、反叛),但必须以事实为骨,不编造因果。

### 8. 本章之变(硬要求,用三级标题)

用 `### 本章之变` 作为小节标题。一段讲"这章结束时项目变成了什么"。承接上一章结尾,回答读者最自然的追问(这章的努力换来了什么,代价是什么,什么遗留问题留给下一章)。只写本章真实发生的变化,不提前透支后面章节的内容。

### 9. 本章关键词(用三级标题)

用 `### 本章关键词` 作为小节标题。结尾提炼三到五个主题词,例如 `架构迁移` `跨平台` `社区回归` `工具链`。

## §10 尾声(经验总结)

三到五条,常见母题按项目实际调整。

- 个人撑起项目 / 团队分工
- 架构复利。早期架构决策如何影响多年后的演进
- 社区价值。issue、论坛呼声如何决定方向
- 技术栈跟随时代。老框架到新框架的迁移动机
- 项目定位。它是什么、不是什么

## §11 论坛回声

与 git 主线并行,分小节叙述,常见的小节有这些。

- 发布之夜。首个 release 帖的社区反应
- 两位开发者 / 核心人物。社区眼中的作者
- 跨平台种子。社区对平台支持的呼声史
- 玩家/用户社区。多年痕迹(如中国玩家的语言需求演变)
- 全球化。多语言 issue、多国参与者
- 热度对照。论坛新帖数对 git 提交数,逐年对照表
- 互文时刻。三个"先有呼声、后有落地"或"代码先行、社区跟进"的时刻,逐条列出论坛帖与对应提交

热度对照表格式。

| 年份 | 论坛新帖数 | git 提交数 | 备注 |
|---|---|---|---|
| 2019 | 12 | 23 | 发布之夜 |
| 2021 | 2 | 9 | 双沉寂 |

## 附录规范

### 附录 A PR 时间线

按年份列出全部 PR,`#N 标题(年份,★ 主题标注)`。★ 用于重大事件,文末注明图例。

### 附录 B 本地 fork 提交清单

存在上游 + 本地 fork 场景时,单独列出 fork 的每条提交(哈希、标题、日期、说明),与上游主线区分。

### 附录 C 论坛数据

- 帖子年度分布表
- 热门帖 TOP N(标题、作者、日期、回复数、浏览数)
- 关键帖 URL 速查表(编号、标题、链接)

## 数据方法论注记(文末)

文末注记要固定写清这几项。

- git log 含 merge 与否
- PR 编号提取规则(从提交消息提取 `#N`,排除误匹配)
- 年份口径(以合入日期为准)
- 大仓库抽样口径(如"仅精读里程碑窗口内提交")
- 论坛覆盖率(如"34 页、667 帖元数据,解析出 633 条;关键帖经镜像交叉验证")
- 推断清单(所有 `[推断:…未证实]` 项的汇总)

## 写作风格硬性要求

1. **双线并行不混写**。git 主线(§2 到 §9)与论坛社区史(§11)分列,靠"互文时刻"交叉引用。
2. **微观与宏观结合**。既保留单条提交细节,也提炼阶段判断("2019 年项目从'能跑'走向'有工具链'"这种句子)。
3. **数据密度**。大量表格、ASCII 图、哈希加 PR 双重索引;每条论断可追溯。
4. **严谨推断**。未证实身份显式标「[推断:…未证实]」;时区推断写明依据(如"+0800 时区推断为中国开发者")。
5. **社会文化视角**。不只看代码,记录用户社区、语言诉求、多国参与。
6. **自我定位意识**。若本仓库是 fork 或重写,将上游历史与"我们的故事"勾连(如注明"#222 的 ogg 支持就是我们 setup 脚本里 `--convert-ogg` 的来源")。

以下几条是"活人感"要求,写作时逐条对照,参考 human-writing 的默认散文写法。

7. **开头碰到事情**。章节的一句话开头要有画面或动作,不要"本章概述"式的起手。宁可从一个反常的小事实讲起("开源当天连发四个版本"),不要预告结构。
8. **句长有节奏**。长句讲事实,短句压判断。不要所有句子等长,也不要用"更深一层""真正的问题"之类路标推进。后段接住前段留下的问题,靠材料和因果衔接,不靠连接词。
9. **动作与场景**。展开重大提交时写具体动作:谁、何时、什么状态、原话。不要干巴巴的"做了什么"。动作、细节、原话已经把情绪写出来,就停,不要追在后面解释。
10. **原话先行**。提交消息原文、文档原话、人物引语,有材料就引用,比转述有力。判断可以偏,可以有情绪,把依据放旁边,让读者知道这是作者的看法。
11. **具体胜过抽象**。数字、哈希、版本号保留;抽象总结句必须有具体支撑,一句话能换进十篇别的文章,说明它没有当前材料。
12. **失败与自我修正**。改错了再改回来、起初以为后来发现,如实写,这是真实感的来源,不要只写成功。
13. **不表演**。戏剧化来自事实本身,不堆大词,不穿论坛服装。判断直接下,不先立误解再推翻。
